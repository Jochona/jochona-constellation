# Virtual-display landscape for game streaming (2026-10)

Research-only survey. Compares `display-adapter` (our fork of
`VirtualDrivers/Virtual-Display-Driver`, MIT/MS-PL, IddCx 1.10, single
fixed slot, protocol v1.0) against the current state of the art. All
facts below are sourced from primary repos/docs linked inline;
anything I could not independently confirm is marked `[UNVERIFIED]`.

### Driver signing (2026 state)

- Microsoft ended the legacy WHCP driver-signing program for Windows 11+/Server 2025+ as of **2026-01-15**; drivers not WHQL- or attestation-signed by that cutover are blocked `[source: HP driver-signing advisory, secondary]`.
- Both WHQL and attestation signing now require an **EV code-signing certificate** tied to a Hardware Dev Center dashboard account ([Driver Code Signing Requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-reqs), [Attestation Sign Windows Drivers](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation)).
- MttVDD and Vibepollo both get free EV-backed signing via **SignPath.io + SignPath Foundation** sponsorship for open-source projects — the same path our `docs/SIGNING.md` already plans to use.
- ARM64 on Windows 11 24H2+ may still require test-signing enabled even for signed third-party IDDs per MttVDD's own comparison-table footnote — `[UNVERIFIED beyond that single footnote]`.

### Capture path (WGC vs DXGI duplication)

- **DXGI Desktop Duplication**: GPU-affine (capturer must run on the same adapter as the display), lower overhead, the traditional Sunshine/OBS path ([OBS forum discussion](https://obsproject.com/forum/threads/windows-graphics-capture-vs-dxgi-desktop-duplication.149320), [Desktop Duplication API docs](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)).
- **Windows Graphics Capture (WGC)**: cross-GPU (works regardless of which adapter renders), is Microsoft's forward-recommended capture API, and — per Vibepollo's README — "in service mode" avoids the historical WGC-under-Session-0 instability, captures the full frame rate of frame-generation titles, survives VRAM exhaustion without crashing, and can capture login/UAC secure-desktop screens that DXGI duplication cannot.
- Neither path appears in `display-adapter` or in `host/src/jochona/display_adapter_client.cpp` — Host's actual encoder/capture pipeline lives elsewhere in `host/src/` and was out of scope for this file-level read, but no zero-copy GPU handoff or direct-swapchain-to-encoder code was found adjacent to the display-adapter client.

### macOS and Linux analogs

- **macOS**: `CGVirtualDisplay` is a **private, undocumented CoreGraphics API** (no public Apple Developer Documentation page) used by Chromium's test harness, `Stengo/DeskPad`-derived tools, and others reverse-engineering the class (`vendorID`/`productID`/`serialNum`/`sizeInMillimeters` fields). Known quirk: changing a virtual display's mode can make it un-removable without a logout `[UNVERIFIED, per go-macos/virtualdisplay package notes]`. This is the only headless-display mechanism on macOS; there is no public, Apple-blessed equivalent of IddCx.
- **Linux**: `drm/vkms` (Virtual Kernel Modesetting) is an in-tree, software-only KMS driver intended for **testing**, not production game streaming — it has no real scanout/capture-performance guarantees ([kernel.org vkms docs](https://docs.kernel.org/gpu/vkms.html)). `VirtualDrivers/Linux-Virtual-Display-Driver` exists as a companion to MttVDD (link only, not independently vetted `[UNVERIFIED]`). Vibepollo's Linux beta ships **its own kernel virtual-display driver** for Arch/CachyOS + KDE Wayland rather than relying on vkms, and SteamOS/Gamescope gets a separate non-virtual-display code path (patched Gamescope HDR10, stock Gamescope SDR) because Gaming Mode doesn't create independent monitors at all.

## 4. What protocol v1.x should gain

In priority order, mapped to the gaps above:

1. **v1.1 — multi-slot pool.** Bump `JOCHONA_PROTOCOL_V1_MAX_SLOTS` (or make it runtime-negotiated via a new `GET_POOL_CAPACITY` IOCTL instead of a compile-time constant), extend `JochonaEnumerateSlotsOut` accordingly. Backward-compatible: old Host binaries requesting v1.0 still see slot 0 behave identically.
2. **v1.1 — HDR metadata fields on `CONFIGURE_SLOT`.** Add mastering-display primaries/luminance and MaxCLL/MaxFALL to `JochonaSlotMode` (or a new optional trailing struct, keeping `#pragma pack(1)` wire stability for existing fields).
3. **v1.1 — per-lease EDID override.** New optional IOCTL (`SET_SLOT_EDID`) so Host can request a specific EDID profile instead of always getting the static baseline; needs a size-bounded buffer (EDID + CTA extension blocks, typically 128–256 bytes).
4. **v1.2 — per-slot render-adapter affinity**, contingent on resolving whether IddCx needs one-adapter-per-slot for true per-monitor GPU pinning (gap #6) — this is an architecture decision, not just a wire-format add, so it should land after #1–#3 prove out the multi-slot model.
5. **No protocol change needed** for hardware cursor (driver-internal DDI wiring only) or for WGC/capture-rate decoupling (already expressible via existing `RefreshNumerator/Denominator`).

Everything above is additive to v1.0's wire format except the pool-capacity constant; `docs/PROTOCOL.md`'s existing status-mapping table and lease/watchdog model need no changes.
