## 1. Current state (verified)

**Host capture (Windows)** — `host/src/platform/windows/display_base.cpp`: `duplication_t::next_frame()` wraps `IDXGIOutputDuplication::AcquireNextFrame` (DXGI Desktop Duplication, line 150). `host/src/platform/windows/display_wgc.cpp`: a second backend using `winrt::Direct3D11CaptureFramePool`/`GraphicsCaptureItem` (Windows.Graphics.Capture). No NvFBC on Windows anywhere in `host/src` — correct, since NVIDIA deprecated NvFBC on Windows 10+ (see §2).

**Host capture (Linux)** — `host/src/platform/linux/{misc.cpp,cuda.cpp}`: NvFBC is implemented and selectable (`source::NVFBC`, `misc.cpp:1109-1344`), CUDA-only capture path (`cuda.cpp:695`, `#include <NvFBC.h>`). No PipeWire/xdg-desktop-portal capture path was found under `host/src/platform/linux`.

**Host capture (macOS)** — `host/src/platform/macos/av_video.m:24,31` uses `AVCaptureSession`/`AVCaptureScreenInput` — the **legacy pre-ScreenCaptureKit AVFoundation API**, not Apple's modern `ScreenCaptureKit` (available since macOS 12.3, Apple's own recommended API for this exact use case — see §2).

**Host encode** — `host/src/video.cpp`: NVENC (`nvenc_encode_session_t`, line 529; encoder tuple `nvenc`, line 699), AMF (`amd_quality_hevc`/`amd_quality_av1`, lines ~975-1001), QSV (`hevc_qsv`/`av1_qsv`, lines 863-943), software x264. All FFmpeg/vendor-SDK based, no Vulkan Video encode path. `host/src/jochona/encoder_tuples.h` already models `backend`/`codec`/`profile`/`chroma`/HDR as first-class proven-tuple keys, including `"pyrowave"` as a codec value (line ~60) and `"metal"` as a backend (line ~56) — the tuple schema is already forward-compatible with a Vulkan PyroWave backend.

**Host PyroWave (already present, narrower than upstream)** — `host/src/pyrowave/pyrowave.h`: Apple-Silicon-Metal-only (`#38`), base profile only — **8-bit 4:2:0, no conditional replenishment, no adaptive FEC/bitrate, no 4:4:4, no HDR** (explicitly scoped out, lines 14-19). Opt-in (`pyrowave_encoder` config, default disabled), gated behind a real probe-encode (`probe()`), never advertised from config/build flags alone.

**Host transport** — `host/src/stream.cpp`: ENet + RTP, Reed-Solomon FEC (`namespace fec`, line 753; `audio_fec_packet_t`, line 298). No WebRTC, no QUIC.

**Client decode/render** — `client/app/streaming/video/ffmpeg-renderers/`: `PlVkRenderer` (`plvk.h`) is a **libplacebo-over-Vulkan renderer already present**, alongside D3D11VA, VAAPI, VDPAU, VideoToolbox, EGL backends. `client/libs/pyrowave-metal/` + `client/app/streaming/video/pyrowave/pyrowavevtdecoder.{h,mm}` decode PyroWave via VideoToolbox — **macOS-only client decode today**, matching the host's Metal-only encode.

**Client/host peripherals already wired beyond gamepads** — `host/src/jochona/capabilities.h:56-70`: touch (`apollo_perm_input_touch`), pen (`apollo_perm_input_pen`), mouse, keyboard, **clipboard read+set** (`apollo_perm_clipboard_set/read`), **file upload/download** (`apollo_perm_file_upload/download`) are all already-defined Apollo-compatible capability bits. `client/app/backend/adapters/hostcapabilities.h:53`: `Clipboard = 0x0002` wired to `GET/POST /actions/clipboard`. Gyro/accel/RGB/battery/rumble already covered in `vibepollo-feature-comparison.md` §2.4 (client `gamepad.cpp`) — not repeated here. 5.1/7.1 surround Opus already implemented (`host/src/audio.h:21-24`, `audio.cpp:25` `opus_multistream_encoder`). No mic/audio-return path found (Moonlight protocol is host→client audio only — not a Jochona gap, a protocol-level fact). No host-side clipboard/file-transfer *implementation* file was located beyond the capability bit — **[UNVERIFIED]** whether `confighttp`'s `/actions/clipboard` endpoint is backed by a working platform clipboard read/write today, or just routes/permission plumbing.

## 7. Top-10 ranked roadmap

1. **Port Solarflare's Vulkan-compute PyroWave host encoder + Aurora's client decoder** (replace/extend Jochona's current Metal-only, base-profile-only PyroWave). Dependencies: Vulkan SDK + `glslangValidator` build-time dependency (`cmake -DSUNSHINE_ENABLE_PYROWAVE=ON` precedent in Solarflare's CMake); needs a new capture→Vulkan-image import path per platform (DXGI/WGC surface on Windows, DRM-PRIME on Linux, IOSurface on macOS). Highest-value item: makes PyroWave cross-platform instead of macOS-exclusive, and Valve just publicly validated the codec class (§6). GPL-3.0→GPL-3.0, clean license.
2. **Migrate macOS host capture from legacy `AVCaptureScreenInput` to `ScreenCaptureKit`** (`host/src/platform/macos/av_video.m`). Apple's own recommended API for this exact use case since macOS 12.3; zero-copy IOSurface hand-off benefits both the existing Metal PyroWave path and a future general capture→encode path. Medium effort, low risk, no dependency on #1.
3. **Add Blackwell NVENC 4:2:2 + AV1 UHQ tuning + Split Encode** to `host/src/video.cpp`'s `nvenc` tuple, gated through the existing `probe_encoders()`/`encoder_tuples.h` proof model. Small-to-medium effort, directly improves quality/throughput for RTX 50-series hosts already in the field.
4. **Port Vibepollo's WGC-service-mode capture** so Jochona Host (which already runs as a service) can capture the lock screen/UAC/elevated content without the current DXGI-DD-via-PsExec workaround — note the open upstream `LizardByte/Sunshine#2846` bug means this needs independent validation, not a blind port.
5. **PipeWire/xdg-desktop-portal capture backend for Linux** (`host/src/platform/linux`) — currently only NvFBC is implemented; non-NVIDIA Linux hosts (AMD/Intel) have no capture path today. Medium effort, fills a real gap.
6. **Verify/extend AMF RDNA4 AV1 quality-preset coverage** in the existing `av1_amf` tuple (`host/src/video.cpp:985`). Small effort, low risk, directly benefits RX 9000-series AMD hosts.
7. **Confirm existing NVENC temporal-AQ/lookahead flag coverage** is current against SDK 13.1 — small effort, closes a possible silent gap (**[UNVERIFIED]** without a full `video.cpp` config-table read).
8. **Adopt the Wayland `color-management-v1` protocol** in the client's Wayland output path once Gamescope/target compositors ship it, replacing any ad hoc `frog-color-management-v1` dependency. Track upstream compositor support before investing engineering time.
9. **Verify the `/actions/clipboard` and file-upload/download endpoints are fully wired to a platform implementation**, not just capability-bit/permission plumbing (**[UNVERIFIED]** — the capability bits and route exist in both `host/src/jochona/capabilities.h` and `client/app/backend/adapters/hostcapabilities.h`, but no host-side clipboard-read/write implementation file was located this pass).
10. **Watch Vulkan Video Encode (H.264/HEVC/AV1) driver maturity** for a future vendor-neutral encode path — not actionable today given confirmed Intel/Mesa encode failures, but AMD RDNA4/RADV AV1 encode is already reported working end-to-end; revisit as Mesa/Intel driver support matures.
